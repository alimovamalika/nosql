# ОТЧЁТ ПО МИНИ-ПРОЕКТУ
## «Каталог электроники с быстрым поиском»

**Дисциплина:** Проектирование и применение NoSQL-технологий  
**Вариант:** 1  
**Технология:** MongoDB  
**Язык программирования:** Python

## 1. Цель работы
Цель мини-проекта — спроектировать и реализовать прототип каталога электроники на MongoDB, который хранит карточки товаров и позволяет быстро находить их по названию, бренду, категории, цене и техническим характеристикам. Дополнительные задачи — реализовать CRUD-операции, агрегирование данных и продемонстрировать назначение индексов.

## 2. Постановка задачи
Интернет-магазину необходимо хранить ассортимент электроники: смартфоны, ноутбуки, наушники, колонки, телевизоры, фотоаппараты, аксессуары и умные часы. У разных категорий отличаются характеристики, поэтому структура данных должна допускать вложенные поля. Пользователь должен иметь возможность находить подходящий товар, а сотрудник магазина — получать статистику и видеть товары с небольшим остатком.

## 3. Функциональные требования
1. Система должна создавать карточку товара с названием, категорией и ценой.
2. Система должна получать карточку товара по идентификатору.
3. Система должна изменять цену товара.
4. Система должна удалять товар по идентификатору.
5. Система должна искать товары по названию или бренду.
6. Система должна фильтровать товары по категории и диапазону цен.
7. Система должна поддерживать фильтрацию по характеристикам во вложенном поле `specs`.
8. Система должна вычислять среднюю цену по каждой категории.
9. Система должна считать число товаров в каждой категории.
10. Система должна показывать товары с остатком ниже заданного порога.

## 4. Нефункциональные требования
1. **Производительность:** типовые запросы должны использовать подходящие индексы там, где это подтверждается планом выполнения.
2. **Расширяемость:** новые характеристики можно добавлять в `specs` без изменения общей структуры коллекции.
3. **Безопасность и воспроизводимость:** конфигурация подключения вынесена в переменные окружения; секреты не должны храниться в репозитории.
4. **Понятность:** код разделён на каталог, скрипт заполнения и тесты.

## 5. Предметная область и модель данных
Основная сущность — товар. Каждый товар хранится отдельным документом коллекции `products`. Поля `_id`, `name`, `category`, `brand`, `price` и `stock` предназначены для идентификации, отображения и фильтрации. Объект `specs` содержит характеристики, которые могут отличаться у разных типов электроники. Например, у ноутбука это объём оперативной памяти и накопителя, у телевизора — диагональ и разрешение, у наушников — беспроводное подключение и шумоподавление.

Пример документа:
```json
{
  "name": "Samsung Galaxy S24",
  "category": "Смартфоны",
  "brand": "Samsung",
  "price": 329990,
  "stock": 9,
  "specs": {
    "memory_gb": 256,
    "color": "серый",
    "screen_inches": 6.2
  }
}
```

## 6. Access Patterns
| № | Паттерн доступа | Приоритет | Ожидаемый результат |
|---|---|---|---|
| 1 | Поиск по названию/бренду | Высокий | До 20 совпадений |
| 2 | Выборка по категории | Высокий | Список товаров категории |
| 3 | Категория + верхняя граница цены | Высокий | Подходящие товары по цене |
| 4 | Диапазон цены | Высокий | Товары между min и max |
| 5 | Фильтр по бренду | Средний | Товары указанного бренда |
| 6 | Фильтр по характеристике | Средний | Товары с нужным значением `specs` |
| 7 | Средняя цена по категории | Средний | Средняя цена и количество |
| 8 | Товары с низким остатком | Средний | Список товаров для пополнения |
| 9 | Получение по `_id` | Высокий | Одна карточка |
| 10 | Изменение или удаление | Средний | Результат CRUD-операции |

## 7. Выбор технологии и архитектура
MongoDB выбрана как документная NoSQL-СУБД. Её модель документов позволяет хранить характеристики разных типов электроники без обязательного одинакового набора столбцов. Aggregation Pipeline используется для статистики по категориям, а индексы — для ускорения типовых фильтров.

Архитектура: пользователь/терминал → Python-приложение (`ElectronicsCatalog`) → драйвер PyMongo → база `electronics_catalog` → коллекция `products`. Скрипт `scripts/seed.py` наполняет коллекцию тестовыми данными и создаёт индексы. Тесты проверяют наличие достаточного объёма синтетических записей и обязательных полей.

Сравнение альтернатив: реляционная СУБД удобна для сложных связей и строгой схемы; Redis лучше подходит для кэша; Cassandra — для масштабируемых временных рядов и событий; Neo4j — для графовых связей. В этой задаче гибкие карточки и фильтрация документов делают MongoDB наиболее подходящим вариантом. Подробное решение зафиксировано в `docs/ADR.md`.

## 8. Индексы
Создаются три индекса:
- составной `category_price_idx` по `category` и `price`;
- `brand_idx` по `brand`;
- текстовый `product_text_idx` по `name` и `brand`.

Составной индекс соответствует частому сценарию выбора категории с ограничением цены. Индекс бренда полезен для поиска по бренду. Текстовый индекс показывает механизм полнотекстового поиска MongoDB. Метод `explain_category_price()` возвращает план выполнения и `executionStats`. Сравнение до/после индекса следует выполнить в MongoDB и зафиксировать фактические `executionStats`; значения нельзя заранее считать измеренными.

## 9. Реализация и демонстрационные запросы
Код находится в `src/catalog.py`. Реализованы методы `create_product`, `get_product`, `update_price`, `delete_product`, `search`, `filter_products`, `average_price_by_category`, `count_by_category`, `low_stock` и `explain_category_price`.

Демонстрационный запуск выполняет восемь типов запросов:
1. Поиск по слову `Apple`.
2. Ноутбуки стоимостью не выше 350 000 ₸.
3. Средняя цена по категориям.
4. Количество товаров в категориях.
5. Товары с остатком не более пяти единиц.
6. Беспроводные наушники.
7. Товары Samsung в заданном диапазоне цен.
8. План выполнения запроса по категории и цене через `explain()`.

## 10. Тестирование
В проект включены три тестовых сценария:
1. Проверка, что тестовый набор содержит не менее 30 товаров.
2. Проверка обязательных полей `name`, `category`, `brand`, `price` и неотрицательной цены.
3. Проверка, что категория каждого товара заполнена.

Команда запуска: `python -m unittest discover -s tests -v`. Эти тесты не требуют соединения с MongoDB, поскольку проверяют тестовый набор. Функциональные запросы к базе следует дополнительно проверить при работающем сервере MongoDB. В отчёте результаты тестов должны быть заполнены после реального запуска.

## 11. Ограничения
Данные синтетические и предназначены только для учебной демонстрации. Прототип не включает авторизацию, пользовательский веб-интерфейс, корзину, оплату и управление заказами. Регулярные выражения подходят для небольшой демонстрации, но не заменяют полноценный поисковый сервис при больших объёмах данных. Результаты производительности зависят от размера коллекции, конфигурации MongoDB и плана выполнения.

## 12. Вывод
В ходе проекта разработана структура каталога электроники на MongoDB и подготовлен Python-прототип для CRUD-операций, поиска, фильтрации и агрегирования. Использование вложенного объекта `specs` позволяет хранить характеристики разных категорий. Индексы отражают основные паттерны доступа, а `explain()` даёт возможность оценить план выполнения запросов. Проект можно расширять новыми категориями, характеристиками и API-интерфейсом.
