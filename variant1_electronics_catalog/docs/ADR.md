# ADR-001: выбор MongoDB для каталога электроники

- **Статус:** принято для учебного прототипа.
- **Контекст:** каталог содержит карточки товаров с неодинаковыми наборами характеристик. Нужны фильтрация, поиск, агрегирование и быстрые типовые запросы.
- **Решение:** использовать MongoDB, коллекцию `products`, один документ на товар. Общие поля (`name`, `category`, `brand`, `price`, `stock`) хранятся на верхнем уровне, переменные характеристики — во вложенном объекте `specs`.
- **Альтернативы:**
  - Реляционная СУБД: хороша для строгих связей и транзакций, но гибкие характеристики требуют дополнительных таблиц или схемных изменений.
  - Redis: эффективен как кэш, но не является основным хранилищем для данного прототипа с запросами и агрегациями.
  - Cassandra: подходит для распределённых потоков и больших объёмов событий, но избыточна для каталога и произвольной фильтрации.
  - Neo4j: удобна для графовых связей, тогда как основной сценарий каталога — фильтрация документов.
- **Последствия:** гибкая схема и встроенные aggregation pipeline; необходимо контролировать согласованность полей и выбирать индексы под реальные запросы. Текстовый индекс демонстрирует поиск по терминам, а регулярное выражение в `search()` является простым демонстрационным поиском; для крупного production-каталога следует отдельно оценить MongoDB Search или другой поисковый движок.
- **Индексы:** составной `{category: 1, price: 1}`, одиночный `{brand: 1}`, текстовый по `name` и `brand`. Перед развёртыванием индексы следует сверить с фактическими паттернами запросов.
